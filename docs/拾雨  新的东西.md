## 一、起点：注销时提示「验证码邮件发送失败」

小喵的怀疑是**前端把密码框和邮箱搞反了**。查下来这个怀疑不成立，但顺带查出真正的故障和另一个更坑的 bug。

### 查证过程

代码层面先看字段绑定，是**对的**、没有错位：

```
user.html:126   <input id="u-delete-password" type="password">   当前密码
user.html:129   <input id="u-delete-code"     type="text">       邮箱验证码
user.js:330     const password = uDeletePassword.value
user.js:331     const code     = uDeleteCode.value.trim()
user.js:311     await window.Auth.sendCode(user.email)       ← 发信只用会话里的邮箱
```

然后直接打线上端点实测，这一步才把问题定死：

| 实测请求 | Supabase 原始返回 |
| --- | --- |
| email = `1234abcd`（怀疑的场景） | `400 Unable to validate email address: invalid format` |
| email = `smoke-test@example.com` | **`500 Error sending confirmation email`** |
| email = `114514@qq.com`（测试 2 号） | `200 {}` |

**结论**：真把密码填进邮箱框，报的是「邮箱格式不正确」，绝不会报 SMTP。所以文案没说错——它说的是**发件邮箱**（SMTP 里那个 From），不是我们输入的收件邮箱。同一时刻 `example.com` 失败、`114514@qq.com` 成功，说明**发信对某些收件域真的会失败**，不是误报。

### 改成什么

原来一句话把所有 SMTP 故障都概括了，**而且让人去改 465 端口——这条建议本身是错的**：Supabase 自定义 SMTP 走 STARTTLS，正确端口是 587，465 是隐式 SSL。照原提示改反而会彻底发不出去。

现在按服务端给的原因分开提示：授权码错 / 连不上服务器 / 发件人被拒 / 通用发信失败。同时 `errorText` 会带上 `error_code` 和 `detail`，并把 `error_id` 打到控制台，拿着它就能去 Supabase 后台 **Logs → Auth** 查这次发信失败的确切原因。

规则顺序上把**具体故障排在兜底规则之前**，否则 `Error sending email: 535 Authentication failed` 会被兜底规则吃掉，白拆。

## 四、Live2D 那两个问题（问过，答完了）

### 1. 两个角色的 Live2D 是同一个吗？

**是同一个。** 四层证据：

| 检查项 | 事实 |
| --- | --- |
| 实际模型文件 | `assets/live2d/` 下只有 `default/`，只有 `ARGNori.model3.json` |
| 已注册模型名 | `live2d.js:16` → `MODEL_NAMES: ["default"]` |
| 星瑶 | `official-roles.js:14` → `model: ""` |
| 月瓷 | `official-roles.js:1454` → `model: ""` |

两个角色都拿到空字符串，`main.js:900` 的 `MODEL_NAMES.indexOf("")` 是 -1，走到 `main.js:910` 的 `return "default"`。连表情动作映射都共用 `models.js` 里那一套。这是**故意留空**等以后配专属模型，不是 bug。

### 2. 「开心 → 13_Happy」什么时候触发？

**触发条件完全由 AI 决定，前端自己不做任何情绪判断。** 链路：

```
main.js:1288  把【情绪规则】追加进 system prompt
                （要求 AI 回复开头先写【情绪：X】，X 从 7 个枚举里选）
   ↓
AI 返回「【情绪：开心】今天天气不错呀。」
   ↓
main.js:1072  parseEmotion() 正则提取，正文去掉标记
   ↓
main.js:1325  Live2D.playEmotion("开心")
   ↓
live2d.js:143 查 models.js → 表情 13_Happy + 动作 Reactions[2]
```

四个硬条件缺一不可：AI 主动写、必须是全角 `【】`、必须在**回复最开头**（正则锚定 `^`）、值必须在 7 个枚举内。

实测的边界情况：

| AI 实际返回 | 结果 |
| --- | --- |
| `【情绪：开心】今天天气不错呀。` | ✅ 播放 `13_Happy` |
| `【情绪:生气】你再说一次。` | ✅ 播放 `03_Angry`（冒号半全角都认） |
| `【情绪：尴尬】…`（枚举外） | ⚠️ **静默不播放**，`if (exp)` 判假就跳过了 |
| `嗯。【情绪：开心】后面才写` | ❌ 不在开头 → 匹配失败，**标记会显示在聊天气泡里** |
| `[情绪：开心]`（半角括号） | ❌ 同上 |

另外发现 **`难过` 和 `委屈` 的动作是同一个** `Reactions[4]`（困扰），表情不同但动作一样，切换时动作上看不出差别。

## 七、踩过的坑（给以后省时间）

| 坑 | 表现 | 怎么处理 |
| --- | --- | --- |
| **PowerShell 写提交信息带 BOM** | `Set-Content -Encoding UTF8` 会加 `EF BB BF`，git 原样收进提交对象，主题行前多个不可见字符 | 改用 `[System.IO.File]::WriteAllText(path, text, New-Object System.Text.UTF8Encoding($false))`，并用字节流验证前 3 字节 |
| **沙箱里 git 推不上去** | schannel 报 `SEC_E_NO_CREDENTIALS`；换 OpenSSL 后卡在 credential helper —— git 在 Windows 上**强制用 `sh -c` 执行 helper**，而沙箱的受限令牌起不了 `sh`（`couldn't create signal pipe`） | 需要提权（danger-full-access）才能推。SSH 也走不通：Git 自带的 `ssh.exe` 一样报 signal pipe，且本机没有 `~/.ssh` |
| **后台任务与前台命令的 `$env:TEMP` 不是同一个目录** | 后台启动脚本报 `MODULE_NOT_FOUND` | 后台命令里用绝对路径，或改用 `node -e` 内联 |
| **`npx` 装不了包** | `npm error EPERM`（沙箱禁止写 `~/.npm-cache`），`npx.ps1` 还会被 PowerShell 执行策略拦 | 自己写最小 DOM 桩做测试，不依赖第三方包 |
| **CSS 同优先级靠后者生效** | `.mp-scrollbar` 和 `.mp-window.flipped .mp-scrollbar` 都是 0,2,0，翻转规则写在前面 → **一直失效** | 翻转规则必须写在默认规则之后 |
| **绝对定位元素不设 width 会塌** | 面板包含块只有 46px 宽，面板就被压成 46px，**里面文字逐字换行变成竖排** | 显式 `width`，并注意别同时设 `left` 和 `right`（会被夹死） |
| **编辑工具会丢文件 BOM** | 改 `index.html` 后开头 `EF BB BF` 没了，于是「完全还原」变成一次多余 diff | 补回 BOM，用 `git diff` 确认零差异 |
| **无头浏览器起不来** | Edge `--headless` 报 `mojo platform_channel Check failed`、crashpad `OpenProcess 拒绝访问` | 沙箱的受限令牌创建不了命名管道。**渲染类问题只能靠人工看**，改用「把数据打印到页面上」让人念数字 |

## 八、周边页装修：换成宇宙引力场背景

这是这一轮的大活儿。**需求和实现都记下来**，因为踩了两个坑、修了一轮，过程比结果值钱。

### 起点

在 `new/ai-combined.html` 里有一张现成的背景：**3000 节点三角形镭射网**（`<canvas id="mesh">`），鼠标移过去引力把粒子吸成亮环、中心被推开形成「宇宙空腔」，点击漾开涟漪。要把它搬进 `zhoubian.html` 当背景，去掉原页面上的搜索框、发送按钮、建议胶囊、对话记录。

### 怎么搬的

从原文件里**整段取出那段 IIFE**，核心逻辑一个字没改——用哈希比对验证过，**6321 字符完全一致**，只多了一行 `if (!canvas) return;` 的防护。

配套的深色适配（不改这一页的 CSS 全局变量，只在这一页内联覆盖）：

| 元素 | 原来 | 现在 |
| --- | --- | --- |
| 页面底色 | `#ffffff` | `#06080d` |
| 导航栏 / 页脚 | 白底黑字 | 半透明深色 + 毛玻璃，文字改浅色 |
| 「周边」标题 / 标语 | `#333` / `#888` | `#eef2fa` / `#9aa4b2`，加 `text-shadow` |
| 🎁 图标 | 无 | 加 `drop-shadow` |

层级：`#mesh` 用 `position: fixed; z-index: 0; pointer-events: none`（鼠标事件穿透到 window，所以整页都能触发引力），内容区 `position: relative; z-index: 1`。

文字也改过一轮：「还在装修中，敬请期待～」→「暂时什么都没有呢 / 看看星星吧」。

### 坑一：页脚跑到了屏幕中间

第一次装上背景后，**页脚（联系站长那一栏）出现在屏幕中间**。

根因是 flex 布局的**两个方向**要同时管住，我第一次只做了一个：

```
body (flex 容器, 高 904px)
  └── main                ← 它是 body 的 flex 子项，默认 flex: 0 1 auto
        ↑ 这里断的：不长大，高度永远等于内容高度（实测 253px）
        └── .wip-page (flex: 1)   ← 只在 main 内部 253px 里分配，撑不开 main
```

第一次只给 `main` 加了 `display: flex`（管内部），页脚没动——因为 `main` 自己不长大，分配来分配去还是 253px。**必须再加 `flex: 1`（管自己作为子项长大）**，链条才通：

```css
main {
    flex: 1;                 /* 管「自己作为子项」长大 */
    display: flex;           /* 管「内部子项能否分配」 */
    flex-direction: column;
}
footer {
    margin-top: auto;        /* 兜底：即使 main 没撑满，页脚也贴底 */
}
```

> **这次的教训**：改 flex 布局不能只看「属性有没有生效」。我在页面上打诊断时看到 `main: display=flex` 就以为是好的，其实要看**尺寸有没有变**（253px 有没有变大）。所以后来我在页面上临时插了个浮层，把 `main`/`footer` 的 `top/bottom/height` 直接印出来，一眼就看出问题——**渲染类问题命令针测不了，就把数据打出来让人念**。

### 坑二：内容被挤到屏幕正中

页脚修好后，`main` 从 253px 撑到 753px，`.wip-page` 跟着变高，而它原本是 `justify-content: center` —— **图标和标语被挪到屏幕正中间了**。

改成靠上排：

```css
.wip-page {
    justify-content: flex-start;
    padding-top: 15vh;      /* 离导航栏留一段距离，不贴着顶 */
}
```

### 性能：一个数字省下 2/3 的 CPU

背景虽然只占 17.4 KB（引用 `style.css` + `common.js` 两个文件，没有第三方库/图片），但**运行时 CPU 开销不小**。我用 Node 跑页面里真实的代码实测（mock canvas + 手动驱动 rAF），发现瓶颈不在节点数，而在**空间哈希的格子尺寸 `CELL`**：

| 配置 | 每帧 | 60fps 预算占用 |
| --- | --- | --- |
| `N=3000, CELL=72`（原版） | **23~37 ms** | 139%~223% ❌ |
| `N=3000, CELL=48`（最终选的） | **约 10 ms** | **60%** ✅ |
| `N=2000, CELL=48` | 15.6 ms | 93% |
| `N=1500, CELL=48` | 8.3 ms | 50% |

**只把 `CELL` 从 72 调到 48，CPU 降到约 1/3，画面看不出区别**，节点数保持 3000 所以网线密度不变。原因：格子越小，每个格子里的点越少，邻居搜索的排序候选集就越小。

> 附带发现：邻居数 `KMB` 从 3 降到 1 几乎不省时间（7.7 → 8.3ms），因为瓶颈不在画线而在物理循环和邻居搜索。

### 两个大光点

又加了两个特殊点：白色和蓝色，带明显光晕，「与其它球逻辑一样但不消散，且屏幕边缘对它们有斥力」。

| | 颜色 | 中心球 | 光晕半径 |
| --- | --- | --- | --- |
| 白色大光点 | `rgba(255,255,255)` | 2.6px | **54px** |
| 蓝色小光点 | `rgba(120,190,255)` | 2.0px | **27px**（正好一半） |

光晕做成三层，和中心球区分明显（半径比 **20.8 : 1**）：外圈 54px 大而淡（0.30→0.08→0）、内圈 11.9px 亮核（0.85→0.25→0）、中心 2.6px 小而实的球。

逻辑与普通节点共用同一套流场 + 鼠标引力公式，只是**不走生命周期**（普通节点会消散重生，它们不会）。边缘斥力：距边缘 150px 内被推回来，越近推得越猛。

**这里也踩了一个坑**：第一次测试发现**两个点最终收敛到同一位置**（相距 0.0px）——因为流场只跟「位置」有关，两个点走到同一处就被同一股力气推着，永远黏在一起，**看起来只有一个点**。修法是给每个点的流场加相位偏移（`fieldAngle(gp.x, gp.y, t + g * 7.5)`），让它们各走各的流线。修完后 3000 帧测试里两点稳定分离。

实测：跑 3000 帧**从未跑出屏幕**（距边缘最近 109.6px）、鼠标引力生效且没被吸进核心、加光点后仍是 10.09ms/帧。

### 手机端：没做适配

按决定**只保证电脑端**。手机实测数据留在这里备查：

| 配置 | 手机 390×844@3x |
| --- | --- |
| `N=3000, CELL=48`（现在这版） | **117 ms/帧 → 约 9 fps** ❌ |
| `N=1500, CELL=24` | 约 26 ms → 38 fps |
| `N=1000, CELL=24` | 约 10.7 ms → 93 fps ✅ |

注意第一行：**手机上画布更小，反而比桌面慢 12 倍**。因为 `CELL=48` 是绝对像素值——桌面 1920 宽切成 40 格，手机 390 宽只切成 8 格，**每格粒子密度高 12 倍**，邻居搜索就爆了。以后要做手机适配，`N` 和 `CELL` 都得跟着屏幕尺寸降。

### 最后一件事：图标和标语不可选中

`.wip-page` 加 `user-select: none`，🎁 图标、「周边」标题、标语都不再参与鼠标拖选（背景动画开着时容易误拖）。只作用在这一块，导航栏和页脚的文字仍可正常选中。
