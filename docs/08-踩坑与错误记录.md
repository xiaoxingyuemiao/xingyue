## 一、怎么记（规则）

1. **当天的坑当天记**，别攒着 —— 隔一天就只剩「好像报过什么错」。
2. 每条必须写清 **四件事**，缺一条这条记录就白写：
   | 项 | 说明 |
   | --- | --- |
   | **现象** | 用户/浏览器看到的是什么（报错原文、界面表现），不要写「不工作」 |
   | **根因** | 真正的原因（不是「那次改了 XX 就好了」） |
   | **修法** | 改了哪个文件哪一行 |
   | **怎么避免** | 下次在什么情况下要想起这条（写成可执行的检查动作） |

### #01 点「➤」不发送消息，点角色按钮反而把消息发出去了（P1）

- **日期**：2026-09-21
- **模块 / 文件**：`index.html`、`assets/js/main.js`（出问题的写法在原第 19 行，改好后在第 21 行）
- **现象**：点 ➤ 完全没反应；点输入框左边的角色按钮，面板打开的同时**输入框里的字被直接发了出去**。回车发送正常，所以很久没被发现。
- **根因**：`const sendButton = document.querySelector(".chat-input button")`。
  `.chat-input` 里的 DOM 顺序是 `角色按钮 → input → 发送按钮`，而 `querySelector` 返回的是**文档顺序第一个**匹配项 —— 拿到的是角色按钮。发送监听器于是绑在角色按钮上。
  （角色按钮自己的 `stopPropagation()` 挡不住**同一元素上**的其它监听器。）
- **修法**：发送按钮加 `id="chat-send"`，改成 `document.querySelector("#chat-send")`。
- **怎么避免**：**按钮一律按 id 取**。看到 `querySelector("某个容器 button")` 这种写法就要警觉：它取的是「第一个」，不是「我脑子里那个」。同一容器里有多个同类元素时，用 id 或 `:last-child`。
- **状态**：✅ 已修（已用无头浏览器核对 DOM 顺序与绑定）

### #02 本地导入的 Live2D 模型必然失败 —— Service Worker 的三层连环坑（P0）

- **日期**：2026-09-21
- **模块 / 文件**：`assets/js/live2d-custom.js`、`l2d-sw.js`（原 `assets/js/l2d-sw.js`）
- **现象**：个人中心「导入本地模型」提示成功，但角色模型加载 404；修到一半又变成界面**永远卡在「正在导入模型文件……」**。
- **根因**：三层问题叠在一起，**少修一层反而更糟**：
  1. **scope 越界**：`register("assets/js/l2d-sw.js", { scope: "/" })`。SW 的作用域不能超出**脚本所在目录**（默认上限就是 `/assets/js/`），请求 `/` 直接抛 `SecurityError`，被 `catch` 吞掉只留一条 console 警告。要用 `Service-Worker-Allowed` 响应头才能放宽，而 **GitHub Pages 发不了自定义响应头**。
  2. **SW 只能拦截「它控制的页面」发出的请求**：把 SW 挪到 `assets/`、scope 改成 `assets/` 之后，注册成功、脚本 200，但虚拟路径**仍然 404** —— 因为 `index.html` / `user.html` 在站点根目录，不在 `assets/` 作用域内，页面发出的请求根本不经过 SW。
  3. **`navigator.serviceWorker.ready` 会永久挂住**：它等的是「**作用域覆盖当前页面**」的 SW。前两层修好后，注册成功了，但 ready 永不 resolve → `importFolder()` 永不返回 → 导入界面卡死。（旧代码因为第 1 层直接抛错、跳过了 ready，所以当时的表象反而是「提示成功」。）
- **修法**：
  - `l2d-sw.js` **移到站点根目录**（和 `index.html` / `user.html` 同级），注册 `siteBase() + "l2d-sw.js"`、scope `siteBase()`；
  - 新增 `waitActivated(reg)` 取代 `navigator.serviceWorker.ready`：等**这个注册**的 `installing/waiting` worker 变成 `activated`，并留 8 秒兜底，避免界面卡死。
- **怎么避免**：**动 Service Worker 时同时看三件事 —— ①脚本放在哪（决定作用域上限）②作用域盖不盖得住「被拦截的请求所在的页面」③等待激活用的是 ready 还是 statechange。** 另外：凡是用 `catch` 吞掉 SW 注册错误的地方，都要把错误**显示出来**，否则用户看到的是「成功」。
- **状态**：✅ 已修（无头浏览器端到端实测：注册 scope=站点根、页面 `controller` 有值、虚拟路径 `200` 并从缓存读回内容，服务器侧收不到该请求）

### #03 验证 SW 时自己踩的坑（方法论，下次省时间）

- **日期**：2026-09-21
- **现象与根因**（都属于「工具/验证手段」而非产品代码）：
  | 坑 | 现象 | 怎么处理 |
  | --- | --- | --- |
  | **`--virtual-time-budget` 快进定时器** | 页面里的 `setTimeout` 超时先触发，真实异步（SW 注册/缓存）还没完成 → 误判成 `TIMEOUT` | 测 SW、缓存、网络这类**真实异步**时不要用虚拟时间；改用「真实时间 + `Start-Process` 启动、Sleep 后 Kill」 |
  | **`--dump-dom` 无输出**（这版 Edge） | stdout/stderr 都是 0 字节，看起来像没跑 | 改用 `--screenshot` 截图，或让页面把结果 `fetch` 回报给本地服务器，从服务器日志读时间线 |
  | **`window.close()` 会取消在途请求** | 最后几条日志上报丢失，误以为步骤没执行 | 收尾不要立刻 close，先 `setTimeout(..., 2000)` 留出发送时间 |
  | **PowerShell 里 `node -e` 多行脚本** | 引号被 PowerShell 吃掉，报 `SyntaxError: Unexpected end of input` | 写成 `.js` 文件再跑，或用单引号包裹、避免 `\"` 转义 |
  | **沙箱受限令牌下浏览器起不来** | Edge 报 `mojo platform_channel Check failed`、crashpad `OpenProcess 拒绝访问`（受限令牌创建不了命名管道） | 这是**沙箱预期行为**，不是系统坏了。渲染类验证需要**一次性提权**（`danger-full-access`）；提权后 `--screenshot` 实测可用 |
- **怎么避免**：凡是「异步 + 环境受限」的验证，**先设计好观察手段**再动手（回报日志 / 截图 / 落盘），不要在结论上猜。

### #05 CSS 3D 翻折「往哪边倒」不能凭感觉写正负号（P2）

- **日期**：2026-09-21
- **模块 / 文件**：`assets/js/auto-preview.js`、`assets/css/auto-preview.css`
- **现象**：自动预览的八向翻折里，有的方向「向后翻」、有的「向前翻」、还有的几乎看不出在动（三种状况混在一起）。
- **根因**：两处错：
  1. 「进入」和「离开」用了**互为相反**的旋转角（`in: rotateX(-90deg)` / `out: rotateX(90deg)`）—— 一边朝屏幕后方倒，另一边必然朝观众倒，方向当然不统一；
  2. 对角方向（左上/右上/左下/右下）的**旋转轴和「折哪条边」没对上**，元素绕了错误的轴，转起来像没动。
- **修法**：每个方向只留**一个**「向后」角度 `back`，进入用它 → 0、离开用 0 → 它（两边转向自然一致）；对角方向的轴改成垂直于对应那条对角线。另外把旧图的淡出改成淡到**全透明**，并让旧图压在新图上面，消掉两图叠着看的「重合」感。
- **怎么避免**：CSS 3D 里 **Z 轴指向观众**，「向后」= 朝 −Z 倒。**不要猜符号**：拿元素四个角做一次罗德里格斯旋转，看四角平均 z 是正还是负（负 = 向后）就定下来了 —— 这次就是这么定出八个方向的。
- **状态**：✅ 已修（数值验证：8 方向 × 进入/离开 = 16 项，z 全为负，且每组的进入与离开 z 完全相同）

### #06 双击 index.html 打开时，Live2D 模型必然不显示（P1）

- **日期**：2026-09-21
- **模块 / 文件**：本地开发方式；新增 `tools/serve.js` + `tools/启动本地预览.bat`
- **现象**：双击 `index.html`（地址栏 `file:///D:/xingyue/index.html`）打开站点，页面和图片都正常，
  **只有 Live2D 模型出不来**；换成 GitHub Pages 或本地 http 服务就正常。
- **根因**：Live2D SDK 要**用 `fetch` 去读** `model3.json`、`ARGNori.moc3`、贴图 PNG。
  在 `file://` 下浏览器的安全策略**一律拒绝这类请求**（文件源的 origin 是 `null`，属于跨源），
  读不到模型数据自然渲染不出来。此外 `file://` **不算安全上下文**，
  本地导入模型依赖的 Service Worker 也注册不了。
  ⚠️ 这**不是站点的 bug**，改站点代码绕不过去 —— 唯一「绕过」办法是把 10MB 模型转成 base64
  内联进 JS，体积和可维护性都不划算，不做。
- **修法**：给一个零依赖的本地静态服务器 + 双击启动器：
  - `tools/serve.js`：只用 Node 自带模块，默认 `http://127.0.0.1:5173`（占用自动往后试），
    自带 MIME 表（`.moc3` → `application/octet-stream`、`.js` → `text/javascript`）、
    `Cache-Control: no-store`、防 `../` 穿越，并自动打开浏览器；
  - `tools/启动本地预览.bat`：双击即用（窗口别关，Ctrl+C 停止）；
  - `package.json` 的 `npm start` 从 `npx serve` 改成 `node tools/serve.js`（离线可用、顺手打开浏览器）。
- **怎么避免**：本地看站**一律走 http**，不要双击 html。README「本地开发」已写明原因和三种方式。
- **状态**：✅ 已加（实测：`/` 与 `index.html` 200 text/html、`ARGNori.model3.json` 200 application/json、
  `ARGNori.moc3` 200 application/octet-stream、贴图 200 image/png、`l2d-sw.js` 200 text/javascript、
  `%2e%2e/package.json` 403、不存在路径 404）

### #07 主页 Live2D 皮套显示正常，但不在正中心（偏左下）（P1）

- **日期**：2026-09-21
- **模块 / 文件**：`assets/css/home.css`（Live2D 段）、`assets/data/models.js`
- **现象**：皮套能正常显示、动作也对，但整体偏在主页左下，不在正中心。
- **根因**：SDK 初始化时会**自己 insert 一个舞台元素** `<div id="oml2d-stage">`，内联样式是
  `position: fixed; left: 0; bottom: 0;` + 宽高等同模型尺寸；它是 `#live2d-container` 的子元素。
  而 `#live2d-container` **带着 transform**（居中用的 `translate(-50%, -50%)`，拖动缩放旋转也靠它）——
  **带 transform 的祖先会让子元素的 `position: fixed` 改以该祖先为参照**，
  于是 `left:0 / bottom:0` 落到了 1050×1500 容器的**左下角**。
  实测对照：容器矩形 `262,-346.5 1050x1500`，画布却在 `262,483.5` —— 正好是容器的左下角
  （左 = 容器 left，上 = 容器 bottom − 670）。
- **修法**：在 `home.css` 里把该舞台拉回容器正中心（容器居中 ⇒ 模型也就落在主页正中心）：
  `left/top: 50% !important` + `transform: translate(-50%, -50%)`，`right/bottom: auto`。
  ⚠️ **必须连 `animation` 一起覆盖**：SDK 的滑入动画（`oml2d-stage-slide-in`）用的就是 `transform`
  且 `fill-mode: forwards`，而**动画在层叠里的优先级高于普通声明（连 `!important` 都压不住）**，
  不覆盖的话自己写的位移会被动画整个吃掉。这里换成自定义的 `xingyue-live2d-in` 保留滑入手感。
  另外：模型"框"居中后，角色像素中心仍比框中心高约 55px（该模型框底部有约 132px 透明留白），
  于是把 `models.js` 里 `default` 的 `position` 从 `null` 改成 `{ x: 0, y: 55 }` 做视觉补偿。
- **怎么避免 / 怎么量**（这次的方法值得复用，但**第一版测量方法是错的**，见第 2 条）：
  1. **不要靠肉眼看**。先量三个 DOM rect 定位问题：容器 rect、`#oml2d-stage` rect、画布 rect ——
     只要「舞台/画布的中心 = 视口中心」，容器这一层就是对的，剩下要查的是模型在画布里的落点。
  2. ⛔ **不要用 `renderer.extract.canvas()` / `extract.pixels()` 量模型在屏幕上的位置**：
     extract 内部会**按目标的包围盒自动平移取景**（等价于 `translate(-bounds.x, -bounds.y)`），
     模型往下移、取景框跟着往下移，**图里看着永远不动**。本次就被它骗了一轮 ——
     据此得出「角色偏高 55px」，虽然补偿方向歪打正着是对的，但**数值与「顶部超出 4px」的结论全是假的**。
     ⚠️ 给 extract 传固定 `frame` **也无效**，它照样按包围盒取景（这一点也实测确认了）。
  3. ✅ **正确量法：读 WebGL 主帧缓冲** —— 在 `renderer` 的 `postrender` 事件里
     `gl.readPixels(0, 0, r.width, r.height, gl.RGBA, gl.UNSIGNED_BYTE, buf)`，
     扫 alpha 求包围盒（注意 **GL 原点在左下，y 要翻**），再按 DPR 换成 CSS 像素、加画布 rect 得屏幕坐标。
     这才是「屏幕上真实渲染的那一帧」，也才能看出 `setModelPosition` 到底有没有生效
     （拿它做 A/B：y=0 与 y=73 两次数值完全不同 → 说明 API 确实生效）。
  4. 用 **CDP 在真实时间下量**：`msedge --headless=new --remote-debugging-port=<空闲端口>`，
     再用 Node 自带的 `fetch` + 全局 `WebSocket`（零依赖）发 `Runtime.evaluate`。
     ⚠️ 端口被上一轮残留实例占着时，`/json/list` 会返回旧目标、`WebSocket` 连接**直接挂住不报错** ——
     所以连接必须**加超时**，并且只清理带 `--remote-debugging-port` 的进程（见下方教训）。
  5. ⛔ **不要用 `--virtual-time-budget` 量**：它快进定时器，SDK 的 resize 队列还没跑完，
     `renderer` 会量成 `0x0`、`stage.children=0`，据此会得出**完全错误**的结论（本次第一轮就踩了）。
  6. ⛔ 别在**同一条连接**里「先 `Runtime.evaluate` 写 localStorage、再 `location.reload()`，接着继续量」——
     reload 会销毁执行上下文，后续求值回包是空的（本次收到一个 `{}`，白折腾一轮）。
     **改用种子页**（临时 HTML：设好 `visited` 标记后 `location.replace("/index.html")`）最稳。
  7. 采样要**多次**：待机动作会让包围盒小幅摆动。
- **最终改法（已验证）**：`models.js` 里 `scale: 0.13`（原 0.10，皮套整体放大 30%）+
  `position: { x: 0, y: 73 }`（往下压，抵消模型框底部约 19.7% 的透明留白）。
- **最终实测**（WebGL 帧缓冲，视口 1574×807）：

  | `position.y` | 角色中心 | 相对视口中心偏移 | 是否被切 |
  | --- | --- | --- | --- |
  | 0 | (782, 332) | (−5, **−71**) | 顶部切掉 3px |
  | 73（当前） | (783, 403) | (−4, **0**） | 没有，完整显示 |

  角色本体尺寸 ≈ 313×665。
- **附带的操作教训**：收尾**不要**用 `Get-Process msedge | Stop-Process -Force` ——
  那会杀掉机器上**所有** Edge 进程，把正在用浏览器的人（站长）的窗口一起关掉。
  只关自己起的那个：`Stop-Process -Id $自己起的PID` 或 `taskkill /PID x /T /F`；
  要成片清理就按命令行筛选：`Get-CimInstance Win32_Process -Filter "Name='msedge.exe'"` 里
  只挑 `CommandLine` 含 `--remote-debugging-port` 的。
- **状态**：✅ 已修并实测（舞台/画布中心从 `(442, 818.5)` → `(787, 403.5)` = 视口中心；
  角色像素中心偏移 `(0, −71)` → `(−4, 0)`，完整显示；站长本人也确认「模型已经在中心了」）

### #08 手机上完全看不见皮套 —— SDK 的 `mobileDisplay` 默认把 ≤768px 的模型整个跳过（P0）

- **日期**：2026-09-22
- **模块 / 文件**：`assets/js/live2d.js`（`buildModels()` / `init()`）、`assets/js/main.js`（启动时机）、`assets/css/home.css`（手机端容器位置）
- **现象**：屏幕宽度 ≤768px 时主页**完全没有皮套**（不是位置不对，是根本没加载）。
  控制台只有一句 `模型锚点设置失败：TypeError: Cannot read properties of undefined (reading 'anchor')`
  —— 因为模型对象压根没创建。
- **根因（两个叠在一起，第一个是主因）**：
  1. **`oh-my-live2d` 的 `mobileDisplay` 默认是 `false`**。它内部用
     `matchMedia("screen and (max-width: 768px)")` 判定手机模式，而
     `get mobileHidden(){ return !this.options.mobileDisplay && ga() === rr.mobile }`，
     `loadModel()` 的第一句就是 **`if (this.mobileHidden) { this.statusBar.rest(); return; }`**
     —— 于是「手机宽度下连模型请求都不会发」。项目初始化时没传这个选项 ⇒ 手机端必然没有模型。
     实测证据：`模型对象不存在`、`renderer 0×0`、`#oml2d-stage` 塌成一行文字高（24px）、容器尺寸正常。
  2. 手机模式下 SDK 读的是 **`mobileScale` / `mobilePosition`**，**不是** `scale` / `position`。
     不传就用它自己的默认值（scale 0.1、位置 0,0）⇒ 即使模型出来了，手机上也会比电脑小、且不居中。
  3. 顺带修掉另一个独立问题：`main.js` 原来在脚本末尾**无条件** `Live2D.init()`，
     而首次访问这几行执行时主页还是 `display:none`（停在登录卡）⇒ 容器尺寸 0×0，
     SDK 建出 0×0 渲染器，**之后再进主页也不会加载模型**（新访客必踩）。
- **修法**：
  - `live2d.js` 初始化选项显式写 `mobileDisplay: true`；
  - `buildModels()` 给每个模型补 `mobileScale`（= 桌面 `scale`）和
    `mobilePosition`（= 桌面 `position`，SDK 要数组所以转成 `[x, y]`）；
  - `main.js` 把 `Live2D.init()` 从脚本末尾挪到「主页真正显示出来之后」：
    新增带防重复启动的 `startLive2D()`，`enterHomeScreen()`（游客进入 / 登录成功）
    与「老用户直接进首页」两条路径都调用它。
- **怎么避免**：
  - 换 / 升级 `oh-my-live2d` 时，先搜 **`mobileDisplay`、`mobileScale`、`mobilePosition`** 三个键的默认值 ——
    它有一整套「手机模式」分支，默认值和电脑模式**不一样**。
  - 任何依赖容器尺寸的第三方库，都要**等容器可见之后再初始化**（`display:none` 时尺寸为 0）。
  - 渲染类问题先量三个数：**模型对象是否存在 → renderer 尺寸 → 帧缓冲非透明像素**，
    再看 CSS 位置。只看 CSS 会得出「位置不对」的错误结论（这次差点又走偏）。
- **状态**：✅ 已修并实测（两种宽度、都走「全新来源 → 登录卡 → 点『先随便逛逛』」这条路）：
  | 视口 | 模型对象 | renderer | 角色尺寸 | 角色中心 | 相对视口中心偏移 |
  | --- | --- | --- | --- | --- | --- |
  | 1574×807（桌面）| ✅ 存在 | 936×1742 | 290×673 | (781, 403.5) | **(−6, 0)** |
  | 496×767（手机宽度）| ✅ 存在 | 936×1742 | 290×673 | (242, 383.5) | **(−6, 0)** |

  顺带的好处：停在登录卡时不再白白下载 10MB 模型（现在进入主页才开始加载）。

### #09 左栏菜单下面莫名多出一条横线 —— `style.css` 的裸 `nav {}` 规则漏进了左栏（P2）

- **日期**：2026-09-22
- **模块 / 文件**：`assets/css/style.css`（`nav {}` 规则 + 新增的两条取消规则）
- **现象**：主页（`index.html`）与个人中心（`user.html`）的**左栏**里，第二个按钮下面总有一条横线
  （主页在「插画」和「周边」之间）。
- **根因**：`style.css` 想把「顶部导航栏」的样式写给 `<nav>`，但写成了**裸元素选择器**：
  `nav { padding: 0 20px; height: 44px; align-items: center; background-color: …; border-bottom: 1px solid …; }`。
  全站一共只有三个 `<nav>`：
  1. `common.js` 注入的 `#site-header > nav`（**本意就是它**）；
  2. `index.html` 的左栏菜单 `<nav class="sidebar-menu">`；
  3. `user.html` 的个人中心左栏 `<nav class="settings-nav">`。
  后两个只声明了 `display / flex-direction / gap`，**没声明 height、padding、align-items、border**，
  于是整套继承下来：菜单被强行压成 44px 高（实际内容 284px），那条 `border-bottom`
  就落在「第二、三个按钮之间」——
  另外 nav 的 `height` 还会让 flex 子项（菜单按钮）被**压缩到 min-content 高度 24px**
  （它们自己声明的是 44px）。
- **修法**：**只取消那一条属性**，其余继承效果原样保留：
  ```css
  .sidebar-menu,
  .settings-nav {
      border-bottom: none;
  }
  ```
- **⚠️ 中间踩的坑（重要）**：第一版修法很"直觉" —— 把裸 `nav {}` 收窄成 `#site-header nav {}`。
  线是没了，但**按钮样子全变了**：左栏 nav 同时失去了 `height: 44px`、`padding: 0 20px`、
  `align-items: center`，于是菜单项从「内容宽 + 居中」变成了**撑满整条侧边栏的宽条**。
  **教训：修「某条 CSS 规则漏到了不该管的地方」时，先分清哪些属性是"你想要的效果"、
  哪些是"副作用"** —— 整体收窄选择器会连带撤掉前者。属性级的最小改动（只改 border）更安全。
  （真要治本，就得在收窄选择器的同时，把左栏需要的那几个属性显式补回去 —— 那属于改外观，要先问站长。）
- **怎么避免 / 怎么量**：
  - 公共 CSS 里**别写裸元素选择器**（`nav {}` / `div {}` / `a {}`…），至少带个类名或上下文限定。
  - 排查「凭空出现的线/边框」最快的办法：扫一遍目标区域内所有元素，
    把「高度 ≤5px、或带上下边框、或带渐变/阴影」的列出来，一眼就能看到是谁画的。
- **状态**：✅ 已修并实测（主页 `nav.sidebar-menu` 与个人中心 `nav.settings-nav`
  `border-bottom` 都是 `0px none`；`height:44px`、`padding`、`align-items:center` 均**原样保留**，
  按钮几何与修改前一致；子页面 `chahua.html` 的顶栏 `#site-header nav` 仍是 `1px solid`，没被误伤）
