# AI 协作约定（两个人 + 各自的 AI 助手）

> 适用仓库：`https://github.com/xiaoxingyuemiao/xingyue.git`（私有仓库，主分支 `main`）
> 本文是 `docs/03-Git协作指南.md` 的补充篇：04 讲「**人**怎么配合」，本文讲「**人 + AI** 怎么配合」。
> 场景：两个真人（站长 / 伙伴），各自用 **DSH** 写代码，共用一个仓库。

---

## 一、为什么还要单独写一份

AI 助手比人快，但也有三个**人不会有的**行为特征。摸清它们，冲突会少一大半：

| AI 的特征 | 会造成什么后果 | 对策 |
| --- | --- | --- |
| **不会自动感知远端更新** | 对方推了新代码，你的 AI 不知道，继续基于旧代码改 → 必冲突 | 每次让 AI 干活前，**先让它执行 `git pull`** |
| **一次改动的「块」很大** | 人冲突可能只差 3 行，AI 可能重写 80 行 → 冲突块巨大、几乎没法手工合 | **按文件分工**，一个文件同一时间只让一个人的 AI 改 |
| **不知道对方的约定** | 朋友的 AI 不知道你改了 `main.js`，你的 AI 也不知道他改了 `home.css` | 约定**写成文件放进仓库**（就是本文），两边 AI 都读得到 |

> 一句话：**AI 更快，所以更需要「划清边界」；人靠默契，AI 靠文件。**

---

## 二、六条铁律

前三条来自 04 手册（人也要遵守），后三条是 AI 协作新增的：

1. **开工先 `git pull`，改完马上 `git push`** —— 推得越勤，重叠窗口越小
2. **永不 `git push --force`，永不批量 `git checkout --ours/--theirs`** —— 这两条是唯一会造成真实数据丢失的操作
3. **冲突解决后必须打开浏览器自测** —— 文本合完了，逻辑可能串了
4. **每次让 AI 动手前，先让它 `git pull`** ⭐ —— AI 不会自己知道远端更新
5. **一个文件同一时间只由一个人的 AI 改** ⭐ —— 撞车概率直接归零
6. **AI 改完要立刻提交推送** ⭐ —— 不允许「改十个文件，晚上一起推」

## 三、给 AI 的标准指令（直接复制粘贴）

### 3.1 开工指令（每次动手前）

```
先执行 git pull，把最新代码同步下来，告诉我同步到了什么。
然后我要做：<用一句话描述任务>
只允许改这些文件：<文件列表>
不要动：<其他文件 / 目录>
```

**为什么要写"只允许改"**：AI 为了省事经常会顺手改别的地方（比如调一下公共样式），那正好是对方负责的文件 → 冲突。

### 3.2 收工指令

```
改完了吗？执行 git add + git commit + git push，
把提交号和改动文件列表告诉我。
```

### 3.3 改完之后的确认（推荐）

```
打开页面自测一下：<要验证的效果>
然后告诉我：改动了哪些文件、有没有碰到公共文件。
```

### 3.4 一句话版（日常最常用）

```
先 pull，然后只改 <文件> 里的 <具体位置>，改完 push。
```

## 四、分工表（**请两人商量后填上**）

> 原则：按**文件**分，不按功能分。填好之后，本文就是两边的"边界地图"。

| 模块 | 涉及文件 | 谁负责 |
| --- | --- | --- |
| 首页 + 聊天 + 登录 | `index.html`、`assets/js/main.js`、`auth.js`、`store.js` | ⬜ 待填 |
| Live2D | `live2d.html`、`live2d-guide.html`、`assets/js/live2d.js`、`live2d-custom.js`、`assets/data/models.js` | ⬜ 待填 |
| 用户设置 + 侧边栏 | `user.html`、`assets/js/user.js` | ⬜ 待填 |
| 个人中心 | `user.html`、`assets/js/user.js`、`assets/js/settings.js` | ⬜ 待填 |
| 插画画廊 | `chahua.html`、`assets/js/gallery.js`、`assets/css/gallery.css` | ⬜ 待填 |
| 周边 / 动态 / 关于页 | `zhoubian.html`、`dongtai.html`、`xingyao.html`、`yueci.html`、`xiaomiao.html`、`assets/js/common.js` | ⬜ 待填 |
| 官方角色设定 | `assets/data/official-roles.js` | 站长（后台维护）|

### 4.1 公共文件（改动前必须打招呼）

这些文件谁都会碰到，**动之前先在聊天里说一句**：「我接下来要动 `home.css`，大概 20 分钟」。

| 文件 | 冲突风险 | 说明 |
| --- | --- | --- |
| `assets/css/home.css` | 🔴 极高 | 首页所有样式都在这，两人都容易加 |
| `assets/css/style.css` | 🟠 高 | 全站公共样式（导航栏、页脚、下载页…）|
| `assets/css/settings.css` | 🟡 中 | 设置页 + 用户设置页共用 |
| `index.html` | 🟠 高 | 首页结构，改版时容易同段撞车 |
| `docs/`、`tools/`、`package.json` | 🟡 中 | 文档与工具，改前说一声 |

### 4.2 减少冲突的黄金规则 ⭐

> **每个页面/模块写自己的独立 CSS 文件，不要都往 `home.css` 里塞。**

正例：插画页用了独立的 `assets/css/gallery.css` —— 这样插画页无论怎么改样式，都不会和首页打架。
反例：两个人分别往 `home.css` 末尾追加样式 → 一小段 `git pull` 就可能冲突。

同理，新增图片时加自己的前缀（如 `a-xxx.png` / `b-xxx.png`），避免同名文件（**二进制文件冲突只能二选一，没法合并**）。

## 五、每天的固定动作

### 5.1 开工（3 步）

```bash
git pull                              # 1. 同步对方（也让 AI 先做这一步）
git log --oneline -5                  # 2. 看看对方最近改了什么
git status                            # 3. 确认自己本地是干净的
```

然后在聊天里说一句：「我今天要做 X，动这几个文件：…」

### 5.2 干活中

- 一次只做一件事，做完就提交，说明写「改了什么 + 为什么」
- **不要让 AI 一口气改十个文件再一起推**

### 5.3 收工（2 步）

```bash
git add . && git commit -m "说明"
git push
```

然后在聊天里说一句：「我推了，这次改了 X / Y」。

## 六、冲突了怎么办（简版）

> 完整流程、坑位表、8 种场景对照，见 `docs/03-Git协作指南.md` 第四节。

```bash
git pull --rebase            # 1. 拉对方的，把自己的改动叠上去
# 2. 有 CONFLICT → 打开文件，删掉 <<<<<<< / ======= / >>>>>>> 三行标记，保留想要的内容
git add 冲突文件              # 3. 标记已解决
git rebase --continue --no-edit   # 4. 继续（--no-edit 避免弹出黑屏编辑器）
git push                     # 5. 打开页面自测后再推

git rebase --abort           # 中途想放弃，回到 pull 之前
```

**AI 协作下的额外建议**：如果冲突块很大（几十行、一片混乱），**别硬合** —— 让一边 `git rebase --abort` 回退，两人商量由谁的 AI 重做这块，比手工拼更快也更不容易出错。

## 七、AI 干活前的自查清单（贴在显眼处）

```
□ 已经 git pull 了吗？
□ 我要改的文件，是不是归我管？（查第四节分工表）
□ 要动公共文件吗？→ 先在聊天里喊一声
□ 改完提交了吗？（别攒着）
□ 推送成功了吗？（被拒就 pull --rebase 再来）
```
